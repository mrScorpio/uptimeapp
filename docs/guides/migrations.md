# Руководство по миграциям базы данных

Инструкция для агентов и разработчиков, меняющих структуру PostgreSQL в UptimeApp.

## Где всё лежит

- `backend/internal/store/store.go` — модели GORM (`User`, `Session`, `Monitor`) и вызов `AutoMigrate`.
- `backend/internal/store/Open` — открывает соединение, проверяет доступность БД и при каждом запуске API применяет `AutoMigrate` к этим моделям.
- `backend/docker-compose.yml` — PostgreSQL 17 для локальной разработки; данные сохраняются в томе `postgres_data`.
- `backend/internal/config/config.go` — читает `DATABASE_URL`, используемый для подключения.
- `backend/docs/` — документация backend.

Сейчас в проекте нет каталога SQL-миграций, таблицы истории миграций или отдельной команды мигратора. Схема создаётся и обновляется GORM `AutoMigrate` при запуске API. Поэтому изменение модели в `store.go` является изменением схемы, которое будет применено при следующем старте API.

## Порядок работы

1. **Разберитесь с текущей схемой и использованием данных.** Проверьте модель в `store.go`, все места чтения и записи соответствующих полей, а также ограничения и индексы в тегах GORM. Не предполагайте, что база пустая: в ней могут быть пользовательские данные.
2. **Выберите совместимое изменение.** Предпочитайте добавление nullable-колонки или колонки с безопасным значением по умолчанию. Для обязательной колонки в таблице с существующими строками сначала добавьте её допускающей `NULL` или с подходящим `default`, заполните существующие строки, затем отдельным шагом вводите `NOT NULL`.
3. **Измените модель и код согласованно.** Добавьте или измените поля, типы, теги индексов и ограничений в модели GORM. Проверьте обработку `NULL`, значения по умолчанию и преобразования на уровне приложения. Новое поле, нужное API, добавьте также в соответствующие DTO/контроллеры и документацию.
4. **Не полагайтесь на `AutoMigrate` для удаления или сложных преобразований.** Не удаляйте поля и не меняйте тип данных с потерей значений, считая, что `AutoMigrate` выполнит безопасный переход. Для переименования используйте переходный период: добавить новое поле, переносить/синхронизировать данные, переключить приложение, и лишь после проверки удалять старое отдельным согласованным изменением. Перед любым ручным SQL или разрушительным преобразованием нужна резервная копия и явный план восстановления.
5. **Учитывайте запуск нескольких версий приложения.** Схема должна оставаться совместимой со старым кодом на время выкладки. Сначала применяйте расширяющие изменения, затем выкладывайте код, который их использует; удаление старой схемы делайте после завершения перехода и отдельного анализа.
6. **Если требуются SQL-миграции или откат, остановитесь и сначала согласуйте/реализуйте переход на версионируемый мигратор.** В репозитории пока не определены инструмент, каталог, формат версий, политика транзакций и команды `up`/`down`. Не создавайте собственный формат миграций или неиспользуемые SQL-файлы: API их не запускает, и они создадут ложное ощущение применённой схемы.

## Как проверить корректность

Выполняйте команды из `backend/`.

1. Запустите проверки Go:

   ```sh
   go test ./...
   go build ./...
   ```

2. Проверьте применение на локальной PostgreSQL, если изменение затрагивает схему. Для локальной базы используйте `docker-compose.yml`, поднимите сервис `postgres`, задайте `DATABASE_URL` и запустите API (`go run ./cmd/api`). Убедитесь, что запуск проходит без ошибок подключения и миграции. Не используйте production или общую базу для пробного запуска.
3. Проверьте результат непосредственно в PostgreSQL: наличие ожидаемых таблиц, колонок, типов, значений по умолчанию, индексов и ограничений. Для каждой новой/изменённой колонки проверьте данные до и после запуска, включая строки, созданные до изменения; убедитесь, что преобразование не потеряло значения.
4. Проверьте основную операцию приложения, читающую и записывающую изменённые данные. Если поддерживаются старый и новый экземпляры приложения одновременно, проверьте их совместимость с промежуточной схемой.
5. Повторно запустите API на той же локальной базе. Повторное применение `AutoMigrate` должно завершиться успешно и не повредить уже существующие данные.
6. В итоговом отчёте укажите затронутые модели/таблицы, что проверено, команды и результат. Отдельно обозначьте ручные действия, резервное копирование или ограничения отката, если они нужны.

`AutoMigrate` не ведёт историю версий и не предоставляет откат миграции. Успешный запуск подтверждает, что GORM смог выполнить своё автоматическое обновление, но сам по себе не подтверждает корректность преобразования существующих данных или совместимость при выкладке.
